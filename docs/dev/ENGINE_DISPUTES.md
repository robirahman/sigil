# Engine rules disputes

Generated by `tools/export_engine_disputes.py`. Open `docs/dev/engine-disputes.html`
to answer the open cases; **no Rust build needed** — the page carries its cases
inline and drives the real game UI, which is the rules oracle.

## Fury: NO BUG. The test is wrong, not the engine.

`tests.rs::greedy_resolution_is_always_among_the_enumerated_outcomes` asserts that
whatever `resolve_spell_at` plays appears in `resolve_outcomes`. Under the fixed
`legal_draw` it failed twice, and that was first reported as a shipped-engine bug
plausibly costing Elo. **It is not.** Over all 1,062 checks:

| outcome | n |
|---|---|
| vacuous: spell not castable in this position | 973 |
| ok | 81 |
| vacuous: enumeration truncated at `OUTCOME_CAP` (4096) | 8 |
| **genuine** | **0** |

The test calls `cast_clear_and_refill` unconditionally, so it asserts the invariant
in positions where the cast is illegal and no resolution can occur.

**Fix:** guard the assertion on the slot's spell appearing in `castable(...)`, and
skip when `EnumStats::resolver_truncated`. No rules question, no engine change.

## key_dash: RULED — full enumeration is missing legal turns

`tests.rs::the_key_dash_filter_never_invents_an_illegal_turn` asserts every dash the
interest filter promotes is also produced by full enumeration. 15 promoted turns are
not — all from one board, all `move a7` then a 2-sacrifice dash sacrificing a11.

```
before: red  a1 a3 a5 a6 a8 a9 a11 a13     red to move, turn 0
        blue b2 b4 b7 b10 b12              counters R0:B0, locks R:- B:-
        spells Corrupt, Hurricane, Seal of Destruction, Fury, Seal of Wind,
               Seal of Stone, Azimuth, Splash, Gust
```

### RULED 2026-09-01 (Robi): a dash MAY land on a node its own sacrifice vacated

> Pointless in general, but the real use is Seal of Lightning + Surge: with every
> stone already optimally placed, lift a stone, put it back where it was, then
> Surge for one more move.

So `dash a11 sac(a11,a3)`, `dash a11 sac(a11,a5)`, `dash a3 sac(a11,a3)` and
`dash a5 sac(a11,a5)` are **legal**. `key_dash` was RIGHT; **`enumerate_turns` omits
them, so the search never considers them.** The ruling lives in `RULINGS` in
`tools/export_engine_disputes.py` so these are not re-asked.

**Fix:** extend turn enumeration to allow a dash destination inside its own
sacrifice set, then re-run the invariant. `key_dash_reasons` ships at 0, so nothing
in production is affected today.

## Two exporter bugs that cost a review round (fixed)

1. `sfnAfter` was built with `apply_turn_tuples` and **no `advance_turn()`**, so the
   target was a MID-TURN state — turn counter unincremented, side to move unflipped.
   The page reported "stones match but counters/locks differ" and no legal turn
   could satisfy it. The locks were identical throughout; the differing fields were
   `turn` and `turncounter`.
2. `stateBefore`/`stateAfter` are the page's ONLY lock display, and the exporter had
   overwritten them with instructions — removing the exact diagnostic needed.

The page's mismatch message now **names the differing fields** rather than saying
"counters/locks differ", so a stale target cannot be mistaken for a rules problem
again.

## Regenerating

```
    --out docs/dev/engine-disputes.html

python -m tools.export_engine_disputes --inplay-games 200
```

The in-play sweep matters because `tests.rs` uses random stone masks; a disagreement
in a position no game can reach costs nothing. Run it before sizing any fix.
