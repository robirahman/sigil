# Step 6: using more than one core (2026-10-06)

Branch `train-s6-multicore`, cut from `providence-bank` at 4b2a2477. Plan section: "Step 6" of
`2026-10-training-plan.md`.

## What was built

**Shared transposition table.** `Search::tt` is now an `Arc<Tt>`: two `AtomicU64` per slot,
written lock-free with the XOR check (Hyatt and Mann), so a slot torn by two writers reads as a
miss. A cloned `Search` shares the table. With one thread the loads and stores are plain moves
and every entry round-trips exactly. The depth-4 bench hash over `harness/positions_midgame.txt`
is `7bb56101eb4761ad` both before (4b2a2477) and after; the depth-5 hash on the VMs is
`27e87b624a08f392` for every 1-thread run.

**`threads` knob** (`Search::set_threads`, default 1, native only; wasm ignores it). Two schemes,
chosen by `set_smp_mode`:

* **0, Lazy SMP.** `threads - 1` helper clones search the same root on the same clock. Helpers
  rotate the root list after the seed move, odd helpers skip alternate depths, and a helper that
  completes a deeper iteration than the main thread supplies the move (`set_smp_vote`, default
  on). The main thread stops the helpers when it returns.
* **1, parallel root.** The helpers form a pool that `root_search` uses on every iteration. The
  main thread searches the first root turn alone, which sets alpha. Then every thread takes the
  remaining root turns from a shared counter and searches each against the best alpha found so
  far (`root_parallel`). Results merge in list order under the sequential loop's rules: a turn
  searched against a higher alpha only ever fails low, which the sequential loop would also
  discard. A fail-high stops the hand-out.

Helpers copy the main thread's per-thread generator switches (`ThreadSwitches`), so an arena
arm that sets a `turn_iter` / `key_dash` / `opening` switch searches with it on every thread.

**Plumbing.**
* `play_best(threads=, smp_mode=)`.
* `ab_search.py` knob `threads`, encoded as threads*10 + mode, with base 10.
* `examples/bench.rs --threads N --mode M --ms BUDGET`, which prints all-thread nodes per second
  and mean depth.
* `harness/smp_bench.py` runs the bench on a VM.

**Tests** (`search::smp_tests`, 173 lib tests pass):
* TT word round trip.
* `threads = 1` gives the identical tree.
* Both schemes terminate (clockless and timed) and return a legal turn.
* Helper threads inherit the switches.
* Root-split parts are disjoint and complete.

## Native scaling (c3d-highcpu-16 = 8 cores / 16 vCPUs; depth 5, 76 midgame positions, clockless)

Time to depth is the main thread's ms. Speedup is the 1-thread ms over the N-thread ms.

| threads | Lazy SMP: ms | speedup | all-thread knps | parallel root: ms | speedup | all-thread nodes vs 1 thread |
|---|---|---|---|---|---|---|
| 1 | 177,120 | 1.00 | 59 | 178,829 | 1.00 | 1.00 |
| 2 | 149,590 | 1.18 | 114 | 113,284 | **1.58** | 1.09 |
| 4 | 145,786 | 1.21 | 197 | 77,632 | **2.30** | 1.20 |
| 8 | 140,489 | 1.26 | 398 | 57,964 | **3.08** | 1.33 |

Lazy SMP scales throughput almost linearly (6.7x nodes/s at 8 threads) but not time to depth.
The helpers mostly re-search the main thread's tree. This engine's table stores only the first
action of the best turn, and node cost is dominated by generating turns, which a table hit
skips only when it cuts. The parallel root wastes little (+9% / +20% / +33% total nodes), and
time to depth falls nearly as fast as cores are added, until hyperthreads share cores.

The best-thread vote never fired in this bench (`helper_won` 0): the odd helpers that skip depths
never completed an iteration deeper than the main thread.

## Arenas: N threads vs 1 thread

Setup:
* Fixed time, colour-swapped, eval `tfit`, on-demand c3d-highcpu-90 (45 cores / 90 vCPUs).
* Every arena ran **smp_mode 1, the parallel root** (`threads` knob = threads*10 + mode, so
  21/41/81 are 2/4/8 threads, mode 1; the base, 10, is 1 thread).
* Pooled from `GAME` lines with `pool_shards.py`. No game went unfinished.
* Shards per VM: the "contended" runs filled the VM, so the arm's threads share physical cores
  through hyperthreading. The low-contention runs used about half the vCPUs.

| run | arm threads | time | shards x threads (vCPUs used) | games | W-L | Elo (95% CI) |
|---|---|---|---|---|---|---|
| 20261006T161504Z | 2 | 3 s | 45 x 2 (90) | 720 | 405-315 | **+43.7 [+18.1, +69.2]** |
| 20261006T161515Z | 4 | 3 s | 22 x 4 (88) | 704 | 380-324 | +27.7 [+2.0, +53.4] |
| 20261006T161527Z | 8 | 3 s | 11 x 8 (88) | 704 | 386-318 | +33.7 [+7.9, +59.4] |
| 20261006T164007Z | 4, low contention | 3 s | 11 x 4 (44) | 704 | 393-311 | **+40.7 [+14.8, +66.5]** |
| 20261006T163955Z | 2 | 10 s | 22 x 2 (44) | 352 | 191-161 | +29.7 [-6.7, +66.0] |

Reading:
* **Every 3 s arm is significantly better than one thread.** That holds at 2, 4 and 8 threads.
* **The gain does not grow with thread count on these VMs.** 4 and 8 threads on hyperthread
  siblings (+28, +34) are no better than 2 threads (+44). With the load halved, 4 threads rise to
  +41. Much of the 4- and 8-thread shortfall is therefore hyperthread contention, not the search.
  Each 8-thread arm had at most 4 physical cores.
* **None of the intervals separate from each other.** The arms are 700 games each, so "2, 4 and
  8 threads are worth about +30 to +45 Elo at 3 s" is what the data supports.
* **The bench predicted more.** The parallel root's time-to-depth speedups (1.6x / 2.3x / 3.1x)
  and the log's 34-66 Elo per doubling of time suggest more than this for 4 and 8 threads. A
  clean 8-thread measurement needs one 8-thread shard per 8 physical cores (e.g. 5 shards on a
  90-vCPU VM).
* **The 10 s run had only 352 games**: the watchdog's 3 h cap ended it. It is positive but does
  not exclude parity.
* **Lazy SMP (mode 0) was not arena-tested.** Its bench time-to-depth gain (1.2x) was too small to
  spend on.

Recommendation: for native play, `threads` with smp_mode 1. Default it to the core count minus
one where it ships (`rust_native`). Before quoting a per-thread-count number, re-measure 4 and 8
threads at low contention.

## Browser, option A (prototype, OFF by default)

**Engine.**
* `Search::set_root_split(part, parts)` keeps only the root turns whose hash
  (`root_part`, an FNV hash of the packed actions) falls in the part. The parts therefore stay
  disjoint and complete whatever order each engine's own table gives its root list.
* An empty part keeps its first turn, so it still answers.
* wasm: `Engine.set_root_split`.

**Worker.** `rust-worker.js` applies `msg.split` to each search and drops it for a ponder.

**Main thread** (`rust-ai.js`):
* a worker pool;
* `rustWorkerCount(requested, hardwareConcurrency)`, capped at `hardwareConcurrency - 1`, default
  1;
* `pickSplitResult`, which takes the best root score among the parts that completed a depth, ties
  to the deeper part, and sums the nodes.

**Behaviour.**
* Enabled only by `RustAI` `options.workers` or `window.SIGIL_RUST_WORKERS`. With 1 worker the
  code path is the shipped one.
* Pondering keeps working: every worker ponders the whole position. The move-time meter follows
  part 0.

**Not shipped.** The committed wasm and `RUST_ENGINE_VERSION` (23) are untouched.
* `build-wasm.sh` takes `WASM_OUT=<dir>` for a prototype build.
* `tools/wasm-smoke.js` takes `SIGIL_WASM_DIR=<dir>`. Against the prototype build it plays 7 split
  moves across 3 engines, with whole-root ponders in between, and every move is replay-verified
  through the real `applyAITurn` gate. Against the shipped wasm the split section skips and
  everything else passes.

**What option A costs, by analogy with the native numbers.** It is the parallel root without the
shared table or the shared alpha. Each worker searches its part with its own alpha and its own
table. Expect it to sit well below the native parallel root's 1.6x / 2.3x / 3.1x. Its scores also
come from separate trees: a part that completed one iteration less can win the comparison on a
shallower, optimistic score.

To ship it, it needs a browser arena (the same tier at N workers against 1, which the fleet
harness cannot run). It also needs a decision about memory: each worker holds its own 16 MB table
at `ttBits` 20.

## Option B (`SharedArrayBuffer` / wasm threads): assessment only, not built

wasm threads would let the browser run the native parallel root (shared table, shared alpha). They
need `crossOriginIsolated`, i.e. COOP `same-origin` plus COEP `require-corp` (or `credentialless`)
on the document. GitHub Pages cannot set headers, so `docs/sw.js` would have to add them to every
response it serves (the coi-serviceworker pattern).

Risks found in `docs/`:

* **Firebase auth popups.** Sign-in uses `signInWithPopup` (Google). COOP `same-origin` severs
  `window.opener` between the page and the popup, so the popup flow breaks.
  `same-origin-allow-popups` keeps popups but does not grant cross-origin isolation. The usual way
  out is `signInWithRedirect`, a real UX change that would need testing on every page that signs
  in.
* **Third-party subresources.** Under COEP `require-corp`, every cross-origin script, style, font
  and image must send CORP/CORS headers. Pages load from `www.gstatic.com` (Firebase SDK),
  `fonts.googleapis.com` / `fonts.gstatic.com`, `use.typekit.net` and `unpkg.com`. Typekit CSS and
  some unpkg assets are known not to send CORP. `credentialless` relaxes this for no-credential
  requests, but Safari does not support it.
* **Firebase Realtime Database.** It uses WebSockets and long-polling to `*.firebaseio.com`.
  WebSockets are exempt from COEP, but the long-poll fallback is a cross-origin script load and
  would need CORP.
* **The service worker becomes load-bearing.** The very first visit (no service worker yet) is not
  isolated, and needs a reload after the worker installs. A failed or stale worker silently drops
  the headers, and the engine must then fall back to single-threaded.

Recommendation: do not pursue option B until option A is measured in a browser. If threads are
wanted later, isolate only the game page and move sign-in to redirect.
